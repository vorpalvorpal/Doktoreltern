# Prior art review: git-backed node stores and plain-text trackers

> Research subagent report, 2026-07-11, commissioned for the mid-flight third-party review.
> External research only. Sister reports: rationale-capture-prior-art.md, agent-orchestration-prior-art.md.

## 1. History of git-native issue trackers: a graveyard with a pattern

**The dead.** The 2005–2012 generation — Bugs Everywhere, ticgit (Scott Chacon), Ditz, Artemis, DisTract, git-case, sciit — is essentially all abandoned. Matěj Cepl's survey of the field describes it as "Landscape after the battle of Verdun, dead bodies and destruction everywhere," with most projects "abandoned even by its original authors" (matej.ceplovi.cz/blog/current-state-of-the-distributed-issue-tracking.html). ticgit's README declares itself dead; driusan/bug last pushed 2019; Google's git-appraise (code review in `refs/notes/`, 5.3k stars) last pushed August 2023 and is effectively unmaintained. git-dit (2017) limps along at ~460 stars.

**Documented causes of death** — from the survey and the May 2025 HN thread on git-bug (news.ycombinator.com/item?id=43971620) — are more specific than "no ecosystem":

- **Worktree file storage caused merge conflicts and churn.** Bugs Everywhere "stored issues in the working tree and caused merge conflicts" (remenos, "Building on Git's Primitives" — small blog, but consistent with Cepl). Cepl's survey adds: UUID-named small files "clog all commit messages," bugs got lost when filed on the wrong branch, and hidden-branch storage made debugging opaque.
- **Non-developers can't participate** (no web input; "normals won't file bugs via git") — the HN thread's dominant objection.
- **Relational data in a non-relational store**: HN commenters flag referential integrity and indexing as the thing that "gets annoying" as data grows.
- Merge conflicts on shared sequential IDs are *not* prominently cited as a killer — mostly because the tools that survived designed them out on day one (below), and the tools that died had already lost users to worktree-file conflicts and missing UIs first.

**The survivors all share one architecture.** Fossil tickets (2007–present, thriving), Gerrit NoteDb (production at Google scale), git-bug (2018–present, ~10k stars, active as of July 2026), and Radicle COBs (Heartwood, 2024; the earlier radicle-link was archived in 2022 and rewritten). Every one stores an **append-only operation log outside any worktree** and derives current state as a materialized view: Fossil replays "ticket change artifacts… in timestamp order" into SQL tables; git-bug stores operation packs as blob/tree/commit DAGs under `refs/bugs/<id>` with Lamport-clock ordering; NoteDb stores "modifications to changes… as a sequence of Git commits"; Radicle issues are Automerge CRDT objects in git storage (RFC 0662; LWN 966869).

**Implications for this store:**
1. **Confirmation:** append-only typed comments folded into views is exactly the surviving architecture. The fold-as-materialized-view is what Fossil, git-bug, and NoteDb all do.
2. **Risk:** a mutable `node.md` per node is the *dead* lineage's pattern (Bugs Everywhere), not the survivors'. Fine single-writer; it becomes the conflict surface the moment there are two.
3. **Non-risk to discount:** most historical deaths were adoption/UI deaths (non-dev access, network effects). A single-user store is immune to those — but it also means no ecosystem tooling will ever appear; you own every viewer, linter, and migration forever.

## 2. Git as an application database: known pitfalls

**Sequential counters are a confirmed anti-pattern for multi-writer — with one instructive exception.** git-bug: entity ID = "hash of the first Operation," displayed as a 7-char prefix, explicitly because offline writers can't coordinate a counter. Fossil: artifact hashes. remenos/grite: UUIDs minted "on any clone without coordination or sequential counters." Radicle: content-addressed COB IDs. The exception is Gerrit, which kept human-friendly sequential change numbers and paid a real engineering price: a `refs/sequences/changes` blob updated by atomic ref CAS with retry, plus **batched range allocation** (`sequenceBatchSize`) to amortize contention — and it only works because all writers funnel through one server. A `_next` file merged by git's textual 3-way merge is strictly worse than any of these: two writers who both increment it either conflict (best case) or silently double-allocate (worst case, if the merge happens to resolve). **Verdict: `_next` is fine today and a known landmine for the multi-agent aspiration. Escape hatches, in ascending effort: serialize all writes through the MCP server; CAS the counter on a ref with retry à la Gerrit; or switch to hash IDs with human aliases à la git-bug.**

**Locking.** Git serializes writes via `.git/index.lock` and per-ref locks; concurrent processes get `fatal: Unable to create '.git/index.lock': File exists`. This is the first thing multi-agent setups hit in practice — current guidance for AI-agent parallelism is retry-with-backoff or per-agent worktrees (which still contend on shared refs) (Claude Code issue #55724; GIT_OPTIONAL_LOCKS discussions). If `ctx_store.py` shells out to git without a retry loop or an in-process write queue, two concurrent writers will break it almost immediately.

**Performance.** Worktree-size costs are real but distant: `git status` degrades noticeably around ~100k files (git-annex tips; Schneider 2016; much of the rest of the search space here is SEO filler — thin evidence, treat bounds as rough). The cliffs that actually hurt git-as-database in production are elsewhere: **ref count** (a Gerrit repo with 500k `refs/changes/*` refs saw flat 11-second fetches from serial ref iteration) and **pack proliferation from frequent small commits**, requiring scheduled `gc`; NoteDb gc leaves thousands of empty ref directories on NFS. For a solo store with thousands of nodes, none of this bites for years. **Performance is the weakest argument against this design; concurrency semantics are the strongest.**

**Fossil's exit is the sharpest critique on file.** Hipp's "Why SQLite Does Not Use Git" attacks git's data model itself (no forward history traversal, poor situational awareness, five-location mental model), and bugtheory.wiki explicitly rejects tickets-as-versioned-files: immutability mismatch, source-tree clutter, and permissions. Because tickets are replayed artifacts, "independently entered changes are automatically merged… Tickets do not branch." Note the store dodges two of Fossil's three objections by living in a separate repo; the third (permissions) is moot solo.

## 3. The plain-markdown school: what breaks first

Evidence here is anecdotal by nature — flagging that — but consistent:

- **Query speed breaks first, at low thousands of items.** Obsidian Tasks scans the whole vault per query; editing lag is measurable at ~1,100 notes and a 40k-note vault is "unusable" for minutes at startup (obsidian-tasks issues #697, #3492). Org-mode's own manual dedicates a section to agenda slowdown; >1,000 agenda files remains infeasible even on Emacs 30 (Worg agenda-optimization). Every mature plain-text system ends up bolting on an index/cache — which the MCP fold layer already is. **Confirmation, with a corollary: the fold must be cached/incremental, not recomputed per query, or it hits the same wall.**
- **Referential integrity is unenforced; the ecosystem's answer is linting.** The markdown world converged on CI link-checkers (remark-validate-links etc.) because renames/moves silently rot links. A store with `nodes/<id>/` references in free text needs its linter to check ID references, not just syntax.
- **Renumber churn:** sequential artifact names invite renumbering, and Cepl documents small-file/ID churn polluting history in the BE era. The `comments/NNNN.md` scheme is a *per-node* sequential counter — same class of problem as `_next`, multiplied: two future writers both creating `0007.md` is a filename collision git cannot merge. Hash- or author+lamport-named comment files would make directory union merge nearly automatic.

## 4. Local-first literature: retrofit merge vs. op-logs from day one

Ink & Switch's local-first essay calls git "perhaps the closest thing we have to a true local-first software package" but names the weakness precisely: file-format-agnostic sync means "inability to perform format-specific merges"; CRDTs merge "at a fine-grained level, tak[ing] datatype semantics into account." The essay does **not** explicitly prove "retrofitting is doomed" — that claim is thin as literature. But the systems record is unanimous: Fossil (2007), git-bug, NoteDb, and Radicle all chose operation logs at design time; Radicle even threw away radicle-link and rebuilt (Heartwood) rather than patch merge semantics on. No surviving system retrofitted concurrent merge onto mutable per-record files.

The honest nuance for this store: **it is closer to an op-log than it looks.** Append-only typed comments + fold ≈ operations + materialized view. Retrofit is viable *if* three things change before the first concurrent writer: (1) collision-free comment filenames (kill the per-node NNNN counter), (2) `_next` replaced or single-writer-guarded, (3) `node.md` demoted to a derived/fold output or given explicit last-writer-wins semantics with history. Git `merge=union` drivers exist for append-only files but live in per-clone config (`.git/info/attributes`) — fragile, don't rely on them. The cheapest correct multi-agent story is the one Gerrit proves: **all writers funnel through one process** (the MCP server as the single committer), reserving true git-merge sync for the cross-machine case that may never come.

**Bottom line:** the fold/append-only architecture matches every survivor in this space — keep it. The three deviations from surviving prior art are `_next`, `NNNN.md` names, and mutable `node.md`; all three are single-writer assumptions wearing file clothing, and all three have known, cheap fixes with named precedents.
