### The loop and its disk artifacts
Artifact root `<root>` = `docs` unless `docs_root` is set in `.compound-engineering/config.yaml` (repo-relative, validated).
1. ce-brainstorm: reads the request, optional repo/learnings context; writes a requirements doc (brainstorm-sections.md; "requirements-only unified plan"). Can render HTML or markdown.
2. ce-plan: reads the brainstorm/origin doc, runs research sub-agents including learnings-researcher against `<root>/solutions/`; writes `<root>/plans/YYYY-MM-DD-HHMM-<type>-<topic>-plan.md` (or .html). Plan model is "status-free" (no done/not-done flag in the file).
3. ce-work: reads the plan (or a prompt); implements via implementation-worker sub-agents / worktrees; then simplify (ce-simplify-code at >=30 substantive lines), then ce-code-review (`mode:agent`, report-only), then the CALLER applies justified fixes (references/review-findings-followup.md), then a Residual Work Gate, then commit/PR. Shipping is "not done" without a completed review receipt (status: complete plus artifact_path/run_id).
4. ce-code-review: reads diff, plan, intent; writes run artifacts to a run dir (per-reviewer JSON, synthesized-findings.json, validator verdicts, report.md or review.json, metadata.json).
5. ce-compound: writes ONE learning to `<root>/solutions/<category>/<slug>.md`; may update CONCEPTS.md and add a discoverability line to AGENTS.md/CLAUDE.md (with consent).
6. ce-compound-refresh: reads all of `<root>/solutions/`, edits/deletes/merges docs, commits.
lfg chains 1..6 hands-off.

### How "compound" captures and reuses lessons (detail)
Trigger and gate (ce-compound/SKILL.md): only after a problem is solved AND verified, and only if it passes a "durable bar" counterfactual: "if the learning document disappeared, would a future engineer reading the final implementation still be likely to repeat the mistake or redo substantial investigation? Completion, effort, and diff size do not establish eligibility." If it fails, write nothing and report why. ce-setup offers a standing directive (assets/compounding-directive.md) to put in CLAUDE.md/AGENTS.md: either "offer once" or "run automatically with mode:non-interactive" at the completion checkpoint, with the same bar.
One learning per run (batching causes cross-reference leakage). Modes: Full (default; parallel research) and Lightweight (single pass, only under context pressure); non-interactive mode asks nothing and ends with `Documentation complete` or `Documentation skipped`.
Process (Full): auto-memory scan; classify and draft body in the main context (it holds the conversation); Related Docs Finder sub-agent greps `<root>/solutions/` frontmatter and scores overlap High/Moderate/Low over five dimensions (problem statement, root cause, solution approach, referenced files, prevention rules); session-history probe; assemble and write; mechanical claims check (scripts/validate-doc-claims.py: code-behaviour claims must cite file:line read at the current tree); semantic grounding-validator sub-agent; frontmatter parser-safety check; optional specialist agents (enhancement.md, interactive only). Sub-agents write scratch files to a per-run /tmp dir and return only the path; only the orchestrator writes product files. Time claims cite PR numbers not SHAs.
File format: markdown with YAML frontmatter, files under `<root>/solutions/<category>/` (build-errors, test-failures, runtime-errors, performance-issues, database-issues, security-issues, ui-bugs, integration-issues, logic-errors, developer-experience, workflow-issues, best-practices, documentation-gaps, architecture-patterns, design-patterns, tooling-decisions, conventions). Corpus-first rule: existing directory names and component/root_cause spellings in the repo win over the defaults. Two tracks:
- Bug track: title, date, category, module, problem_type (enum), component, symptoms[1-5], root_cause, resolution_type, severity (critical/high/medium/low), optional retire_when, tags. Body: Problem, Symptoms, What Didn't Work, Solution, Why This Works, Prevention, Related Issues.
- Knowledge track: same shared fields plus applies_when[]; body: Context, Guidance, Why This Matters, When to Apply, Examples, Related.
Optional `retire_when` records the external change (upstream bug fixed, version) that would retire the lesson and how to check it. YAML safety rules (quote leading backticks etc.).
Vocabulary: a root CONCEPTS.md holds shared domain terms; ce-compound seeds terms from its own area; the Related Docs Finder and learnings-researcher read it for keyword grounding.
Retrieval (reuse): (a) ce-plan dispatches learnings-researcher with a `<work-context>` block (Activity, Concepts, Decisions, Domains). It reads CONCEPTS.md, discovers which category dirs exist, runs parallel case-insensitive greps against frontmatter fields (title, tags, module, component, applies_when), re-runs narrower if >25 candidates and broader if <3, reads only the first ~30 lines of candidates to score, fully reads only strong matches, and returns distilled "constraints, sequencing risks, patterns to follow, failed approaches to avoid, solution docs to read". (b) ce-code-review has a conditional `learnings` persona that does the same against the diff, selected only when a cheap pre-search finds a plausible match; a Compound Pack rule that the diff contradicts becomes a numbered finding. (c) ce-brainstorm/ideate/optimize also use learnings-researcher. (d) A "Discoverability Check" every run ensures AGENTS.md/CLAUDE.md tells agents the store exists, how it is organised (category dirs + frontmatter fields) and when to search it; it adds the smallest possible line, only with consent (interactive) or reports the gap. There is no index file or embedding; retrieval is grep over frontmatter plus model judgement. Compound Packs (small prescriptive rule files with `applies_when`, declared in config) are a second, hand-curated search root that is read in full rather than grepped.
Preventing unbounded growth (this is the interesting part):
1. Admission gate: the durable-bar counterfactual (most fixes write nothing); one learning per run.
2. Dedup at write time: Related Docs Finder overlap score; High overlap or materially stale old doc means UPDATE the existing doc rather than create a duplicate ("An existing learning that became materially inaccurate ... Update that learning instead of creating a duplicate").
3. Maintenance skill ce-compound-refresh with five outcomes per doc: Keep / Update / Consolidate (merge unique content into canonical doc, delete the other) / Replace (new doc via sub-agent, delete old) / Delete. "Git history is the archive; there is no _archived/". Age alone is not staleness; "unverifiable is not false"; auto-delete only if implementation and problem domain are gone and inbound citations are decorative. ce-compound recommends a narrowly scoped refresh after writing when overlap is moderate or an older doc is contradicted (never auto-runs in non-interactive mode).
4. Optional "worth audit" (only when the user asks to cull/prune): deletes or shortens accurate docs whose reasoning is already stated in a test, code comment or the instructions file, quoting that file for every cut. Consolidation test: "would a maintainer searching this topic in six months benefit from separate docs ... or do they just create drift risk? Two docs saying the same thing will eventually say different things."
5. Retirement: `retire_when` lets refresh check an external condition.
No size cap or summarisation tier exists; control is admission + consolidation + deletion + grep-first retrieval that never loads the whole store.
Relevance to werkbank retrospective phase: the durable-bar wording, the frontmatter schema with `applies_when`/`retire_when`, the Keep/Update/Consolidate/Replace/Delete classification, and the grep-first learnings-researcher are directly liftable. Note it captures per-solved-problem lessons, not process/cost retrospectives; nothing reads cost or run reports.

### Review agents (ce-code-review)
Personas (references/personas/*.md): always correctness; project-standards (only if applicable standards files found); conditional by diff: testing, maintainability (>=200 changed lines/structural), agent-native, learnings, security, performance, api-contract, data-migration (plus deployment-verification-agent), reliability, adversarial (>=50 lines or high-risk areas; runs through an independent cross-model peer where one can be started, else in-process), previous-comments (PR with prior comments); stack-specific: julik-frontend-races, swift-ios. Selection is by the orchestrator reading the diff, with one-line justification announced. Also a fast inline pass ("fast-pass") before the personas, capped at confidence 50. ce-doc-review personas for plans/specs: coherence, feasibility, product-lens, design-lens, security-lens, scope-guardian, adversarial-document, whole-doc.
Finding form (references/findings-schema.json): JSON per reviewer {reviewer, findings[], residual_risks[], testing_gaps[]}; each finding has title, severity P0-P3, file, line, why_it_matters, autofix_class (e.g. gated_auto/manual/...), owner (e.g. downstream-resolver), requires_verification, confidence as a discrete anchor 0/25/50/75/100 (0 and 25 are never emitted), evidence[] whose first item MUST be the verbatim motivating line with file:line for anchors 75/100 (the "quote-the-line gate"), pre_existing flag, suggested_fix. Reviewers write the full JSON to run_dir and return a compact version.
Merge/dedupe (references/finish-review.md Stage 5): scripts/findings-mechanics.py does schema validation, exact-fingerprint dedup (normalised file + line + lowercased title), quote/confidence checks, deterministic sort and stable numbering. Independent agreement between reviewers promotes confidence (a 'cross-reviewer promotion'); in-process fast-pass never counts, only independent reviewers/cross-model peer. A model pass then does semantic reconciliation: "Merge differently worded findings only when they describe the same defect and fix path. Keep disagreements visible." When reviewers disagree on route, keep the more cautious class. Then a confidence threshold, soft-bucket demotion, a separate validator sub-agent that re-verifies the P0/P1 (up to 8) findings independently (confirmed / dropped / unresolved; unresolved P0/P1 stay as "verification gate" and block a "Ready to merge" verdict), then triage grouping and report with Verdict (Ready / Ready with fixes / Not ready). Severity bar is Google's "improves overall code health, not perfect".

## Part C: published approaches to the two problems

### (1) Clustering findings so one root cause is fixed once
Partly addressed in compound-engineering; nobody addresses it as a first-class fix-once mechanism.
- Display-level grouping only. ce-code-review finish-review.md Stage 5 step 6, "Build thematic triage groups": "Group related findings so the reader can triage themes instead of items. This is distinct from deduplication: groups never merge findings or change severity, confidence, route, owner, or stable `#`." Signals: "shared root cause, affected subsystem, user-facing failure mode, overlapping fix path, dependency ordering, or repeated symptoms of one design choice." "When one fix path resolves several findings, name it and say which finding to handle first." The report says: "Group findings sharing a root cause or one fix" and "A multi-file applied fix is one row with one `#`". Groups are advisory; they do not change what a fixer is dispatched on.
- Semantic merge: "Merge differently worded findings only when they describe the same defect and fix path." (merges identical defects across reviewers, not different symptoms of one cause).
- Class fix in ce-resolve-pr-feedback/references/evaluation-rubric.md: "A validated finding can span sites this PR itself introduced (fix the class, not one instance)... check whether this change also introduced or touched other sites governed by the same invariant that admit the same fix with no site-specific judgment. When those sites are concretely identifiable and their treatment is unambiguous, fold them into one class fix ... Keep the class narrow ... If equivalence or treatment is itself a judgment call, keep them separate items — a false 'class complete' is worse than one more round." Also a "wrong-reviewer cluster" notion in the same file.
- Recurrence signal: full-mode.md: after the second fix-verify cycle stop looping: "Multiple rounds of feedback on [area/theme] suggest a deeper issue."
Not found: any step that clusters findings by root cause BEFORE dispatch so a single implementer gets the cluster; any cluster-level re-test.

### (2) Review "fixes" introducing new bugs
Several guardrails, no re-review loop.
- Verify-then-keep (finish-review.md Stage 5c): "After applying, run the affected tests and lint ... If they fail, revert that fix and report it as a finding instead; an unverified fix is not finished. Never leave the tree red."
- Self-review of the autofix diff: "diff only the changes introduced during Stage 5c against the pre-apply checkpoint. Run one self-review pass over that diff" (duplicated helpers, broadened input contracts); re-run tests if it changes files.
- Flag green-but-unverifiable edits: "When an applied fix touches auth/authz, a public or cross-service contract/schema, or concurrency/ordering, a passing test does not prove safety. Flag it prominently."
- Never apply unvalidated findings: a finding left `unresolved` by the validator is "never applied". Report-only by default; commit fixes as one isolated `fix(review):` commit only if the tree was clean, so it is revertible; never push.
- Separation of roles: `mode:agent` review never mutates; the caller (ce-work) decides which fixes to apply and dispatches fixers.
- ce-resolve-pr-feedback: "A finding on code an earlier review fix added asks whether that fix was the right layer" (check git blame for review-fix commits; don't stack another layer when failure is already bounded); declines fixes that "make the code worse"; parallel fixers that collide are re-run sequentially; red validation touching the change set gets one diagnose-and-fix pass, then `needs-human` and no commit; max two fix-verify cycles per PR (counted from earlier review-fix commits on the branch) before escalating.
Not found: an explicit second full review of the fix diff by independent reviewers, or a regression-test-first requirement for each review fix (ce-dogfood does add regression tests for its own autonomous fixes, which I only saw in its description).
