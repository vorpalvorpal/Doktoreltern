# Leitstand research: SDK session control and front-ends (2026-10-06)

Marks: quoted = from the cited page; INFERRED = my reasoning; UNCONFIRMED = no source found.
Doc root: https://code.claude.com/docs/en/ . GitHub numbers fetched 2026-10-06 with `gh api`.

## Headline

Resume-at-a-chosen-message EXISTS in both Agent SDKs and the CLI plumbing, as of TS SDK 0.3.223+ / Python SDK 0.2.137+ / Claude Code v2.1.223+.

- TS option `resumeSessionAt` (string): "Resume session at a specific message UUID" (https://code.claude.com/docs/en/agent-sdk/typescript, Options table).
- Python `resume_session_at`: "When resuming, load the conversation only up to and including the message with this UUID. Use with `resume`, and usually `fork_session`, to branch from an earlier point. Requires Python Agent SDK 0.2.137 or later" (https://code.claude.com/docs/en/agent-sdk/python, ClaudeAgentOptions).
- Companion `resumeDropsTurn`: "With `resumeSessionAt`: the prompt UUID of the turn the truncating resume intends to discard. Claude Code refuses the resume when the discarded range contains anything not attributable to that turn, such as absorbed queued messages or task notifications ... Only the Agent SDK and print-mode resumes read the pair. Requires Claude Code v2.1.223 or later" (TS reference). The wording "truncating resume" shows that without `forkSession` it truncates the original session; with `forkSession` it branches. Whether the truncated-away tail is physically deleted from the .jsonl or only masked: UNCONFIRMED.
- Standalone function: TS SDK changelog 0.2.76 "Added `forkSession(sessionId, opts?)` for branching conversations from a point"; a later entry mentions `forkSession({ upToMessageId })` (https://github.com/anthropics/claude-agent-sdk-typescript/blob/main/CHANGELOG.md). Python has `fork_session()` (Python CHANGELOG, "Added `fork_session()`, `delete_session()`..."). Exact signatures not fetched from the reference page: UNCONFIRMED beyond the changelog.
- What identifies the message: its UUID. Python doc: "Use these [list_sessions / get_session_messages / get_session_info] to find message UUIDs for `resume_session_at`." Checkpoint UUIDs are the UUIDs of user messages, available when `--replay-user-messages` is set ("each user message in the response stream has a UUID"; https://code.claude.com/docs/en/agent-sdk/file-checkpointing).
- Whether a UUID of a user message vs an assistant message is the right cut point for "just after [spec][plan]": the Python example uses a generic "<message-uuid>"; the TS fork fix notes mention cutting at "a progress row" and "fork briefing" edge cases. Cut at an assistant message that closes a turn is INFERRED to be the safe choice; test it.

## Q2. Prompt cache

- https://code.claude.com/docs/en/prompt-caching: "The API caches by matching the start of each request, called the prefix ... The match is exact, so a change anywhere in the prefix recomputes everything after it."
- Rewind in the TUI: "`/rewind` truncates your conversation back to an earlier turn. The remaining history is the same content the cache was built from at that point, and the system prompt and project context layers are unchanged, so the next request hits the earlier cache entry." (matches your measurement).
- Resume: "When you resume a session, Claude Code sends the whole conversation again, and the request reads from the cache whatever part of its prefix is unchanged and still within the cache lifetime." By default a resumed conversation keeps the system prompt it started with (recorded on the first request), which is what makes the prefix reusable.
- Docs say NOTHING specific about `resumeSessionAt` or SDK fork and cache. INFERRED: because it re-sends the truncated history, the same prefix rule applies, so a resume-at to just after [spec][plan] should hit the earlier cache entry while that entry is within TTL. Caveats that break the match: different model, effort (on most models), tool-definition set (MCP/plugin changes), system-prompt flags if not snapshotted, and Claude Code upgrade. Must be measured (cache_read_input_tokens on first turn after resume-at).
- TTL: main conversation gets one hour only "on a Claude subscription within your plan's included usage"; five minutes on API key / cloud provider unless `promptCacheTtl` / `CLAUDE_CODE_PROMPT_CACHE_TTL=1h`. Subagents/everything else five minutes. Quote: "Each request that hits the cache resets the timer". A rewound-to prefix stays warm because "Every turn since then has read through that prefix".
- Cache is "effectively scoped to one machine and directory" (cwd embedded in the prompt); an SDK process must use the same `cwd`. Sessions in the same directory "read each other's cache".
- A forked session "(fork of a subagent) inherits the parent's system prompt ... so its first request reads the parent's cache" is about in-session subagent forks, not SDK fork; do not conflate.
- Also: the sessions page warns on resume after >1 hour on Pro/Max with over 100k tokens, a "Resume from summary" dialog appears (TUI only). Not relevant to SDK path (INFERRED).

## Q3. Official ways for a human to watch and talk to a session someone else drives

| Surface | Can human type into a session a program drives? Live output? |
|---|---|
| Native TUI `claude --resume <id>` on an SDK-created session | Resume works from any directory by id ("You can still resume one by passing its session ID", sessions page). But it loads the transcript into a NEW process. Two processes on one session: "If you resume the same session in two terminals without forking, messages from both interleave into one transcript." Neither process sees the other's turns live (INFERRED; docs say only interleave). No coordination: not safe for a driver plus a human. Good for post-hoc inspection when the driver is idle. |
| Remote Control (`claude --remote-control`, `/remote-control`, `claude remote-control` server mode) | https://code.claude.com/docs/en/remote-control: "Work from both surfaces at once: ... you can send messages from your terminal, browser, and phone interchangeably." That is for an INTERACTIVE session (or server mode, "no local interactive session") started by Claude Code itself. Requires claude.ai subscription: "API keys are not supported." The page's limitations say "One remote session per interactive process". I found no statement that an Agent SDK or `-p` process can enable Remote Control: UNCONFIRMED (likely no). A deterministic driver typing into an interactive TUI session still needs a keystroke/pty path. |
| claude.ai/code cloud sessions, `claude --cloud`, `--teleport` | Cloud sessions run on Anthropic/self-hosted infra, not your local session. `--cloud` "With a session ID ... queue a message into that existing session instead, with `-p`" (CLI ref): a program can queue a message into a cloud session while a human watches at claude.ai/code. `--teleport` "Resume a cloud session in your local terminal". Does not give resume-at control; cloud-session rewind: UNCONFIRMED. Runs on cloud env, not Robin's machine (self-hosted environments exist: `claude self-hosted-runner`). |
| Background sessions / agent view (`claude --bg`, `claude agents`, `claude attach <id>`, `claude logs`) | https://code.claude.com/docs/en/agent-view. A supervisor hosts the session; `claude attach` gives a full interactive TUI on it; `claude logs <id>` prints recent output. Docs (as summarised from the page) list no CLI to send a prompt to a running background session other than attaching or `claude --resume <id> "prompt"` (which per the sessions page "goes to it as its next turn"), and `--bg` cannot be combined with `-p`. So a driver can inject turns via `claude --resume <bg-id> "prompt"` and a human can `claude attach` at the same time. This is the only OFFICIAL shared-session path I found that has a human TUI on the same live process as a programmatic injector. But there is no resume-at inside it, and respawn only "with its conversation intact". Whether the driver prompt arrives with the human's typing queued safely: UNCONFIRMED. Research-preview feature (agent view shipped 2026-05-11 per a third-party article, https://claudefa.st/blog/guide/agents/agent-view; verify). |
| Claude Desktop app | `claude --desktop --resume <id>` "open that session in Desktop" (CLI ref, v2.1.285+). It opens the session in the app's own process, not a shared live one: INFERRED. |
| VS Code extension | Keeps "their own session list" (sessions page). No evidence of attaching to an SDK-driven process: UNCONFIRMED. |

Bottom line (INFERRED): the official surfaces give a human a view onto a session that Claude Code itself hosts. None lets a human TUI attach to an SDK-owned in-process session. The SDK stream is the source of truth, so the front-end has to be fed from the driver's event stream.

## Q5. Build-it-ourselves (SDK-owned session, thin terminal front-end)

How small: the SDK docs' own examples are 20-40 lines for a loop that streams messages and sends follow-ups (streaming-vs-single-mode page; sessions page). A usable front-end is: one `query()` with an async generator input queue (stdin lines pushed in), an event printer for `assistant`/`result`/`system` messages (with `includePartialMessages` for live text), a key binding calling `query.interrupt()`, `setPermissionMode`, and the driver calling `forkSession`+`resumeSessionAt` between steps. Estimate 150-400 lines of TypeScript for a bare version; a decent one (readline with a pinned prompt line, colours, status line) is INFERRED at a few hundred more. Official demos: https://github.com/anthropics/claude-agent-sdk-demos (not inspected).

What the native TUI gives that is lost or must be rebuilt (INFERRED unless quoted):
- Permission prompts: SDK "surfaces permission requests" to your code via `canUseTool` / `--permission-prompt-tool`; you render them. For an unattended build set a mode or `--permission-prompts none` ("Pass `none` when nobody can answer, and Claude Code denies them instead", CLI ref).
- Slash commands: some work typed into SDK sessions ("`/reload-plugins` also runs in sessions without an interactive terminal, such as ... the Agent SDK ... when you type it into the session directly", prompt-caching page). Interactive ones (`/model` picker, `/resume`, `/rewind`) do not exist as UI.
- Skills and commands load: "Skills, commands, and memory | Load automatically from your project's `.claude/` and from `~/.claude/`, same as Claude Code" (https://code.claude.com/docs/en/agent-sdk/overview).
- Settings and hooks load by default: "When you omit `settingSources`, `query()` reads the same filesystem settings as the Claude Code CLI: user, project, and local settings, CLAUDE.md files, and `.claude/` skills, agents, and commands." Filesystem hooks: "shell commands defined in `settings.json`, loaded when `settingSources` includes the relevant source" (https://code.claude.com/docs/en/agent-sdk/claude-code-features). Python gotcha: older SDKs defaulted differently; the doc quoted says default all, check your installed version.
- Plugins: option `plugins` defaults `[]` ("Load custom plugins from local paths", TS ref); https://code.claude.com/docs/en/agent-sdk/plugins covers it. Whether INSTALLED plugins (marketplace, enabled in user settings) also load in SDK sessions: UNCONFIRMED from what I fetched (`--bare` is described as skipping "installed plugins", which implies non-bare loads them; INFERRED yes).
- Your "mods" (live panes, bands, status lines rendered in the TUI): their logic hooks run headless per your experiment, but anything that RENDERS in the Claude Code TUI will not appear; the status line command is a TUI feature. UNCONFIRMED whether SDK emits status-line data (the `statusline` fields come from the TUI).
- Sub-agent display: only via the stream: `--forward-subagent-text` flag ("Emit subagent text and thinking blocks ... with `parent_tool_use_id` set"), you render the tree yourself. TS `Task*` messages: UNCONFIRMED.
- Scrollback: your terminal's; nothing special.
- `--resume` compatibility: SDK sessions are normal transcripts; `claude --resume <id>` opens them (not in the picker: "Claude Code leaves sessions created with `claude -p` or the Agent SDK out of the session picker and out of `claude --continue`", resume by id works). After a truncating resume-at, what the native TUI shows (stale tail?): UNCONFIRMED; fork-based resume-at gives a clean new transcript, so prefer fork.
- Auth caveat: "Unless previously approved, Anthropic does not allow third party developers to offer claude.ai login or rate limits for their products, including agents built on the Claude Agent SDK. Use the API key authentication methods" (agent-sdk overview). This is about products offered to others. A personal tool on your own login: INFERRED fine, but note Remote Control is claude.ai-login only, and API-key billing changes cache TTL to 5 minutes by default (set `promptCacheTtl=1h`).
- Driver reads: do not parse the .jsonl; use the stream and `getSessionMessages`.

## Q6. Recommendation

Pick (b): SDK-owned session with our own thin terminal front-end, with a fallback of (a) per phase until (b) is measured.

Reasoning:
1. Resume-at plus fork exist officially and are SDK-native, replacing the three mod tricks and the fragile keystroke wrapper. One process owns the session and is the only writer, so there is no two-writer interleave.
2. Robin's three needs (updates, progress, "say stop") map directly onto the event stream, `interrupt()`, `streamInput`, and `setPermissionMode`.
3. Attaching (c) fails on the key requirement: no third-party tool found can attach as a live peer to an SDK process another program owns; claude-squad and cmux wrap a pty (the fragile path); Happy, claudecodeui, vibe-kanban own their spawn. The official Remote Control has no confirmed path for SDK/-p sessions.
4. Official fallback worth a spike: background session (`claude --bg`) with `claude attach` for Robin and `claude --resume <id> "prompt"` for the driver. It keeps the native TUI and mods rendering but has no resume-at. Treat as a variant of (a), not (b).

Must-measure before committing: (i) `resumeSessionAt` + `forkSession` cut at the closing assistant message of [spec][plan] gives `cache_read_input_tokens` ~ the prefix on the next turn, with same cwd/model/effort/tools; (ii) your mods' hooks and plugin loading under SDK with default `settingSources`; (iii) the TUI's `--resume` view of a forked session.

Strongest argument against (b): you give up the official TUI, which carries the mod UI (panes, status line), permission dialogs, slash commands and sub-agent display, so the front-end you write is a permanent maintenance burden against a fast-moving SDK (the V2 session API was removed in 0.3.142; the resume-at feature is only a few releases old, 0.3.223 / Python 0.2.137, and the transcript format "changes between versions"). If the cache-hit measurement in (i) fails or `resumeSessionAt` cut points prove flaky, (b) loses its main advantage and (a), which already works, is the better choice.
