# Research: failing-test audits, Rust-only (2026-10-06)

Evidence labels: SOURCED = found this session (URL given); KNOWLEDGE = my prior knowledge, not re-verified; UNSOURCED = could not source. Search tool results were thin in places; treat KNOWLEDGE as plausible, not checked.

## Q1a. Property-based testing in Rust, 2026

- proptest: the default. Strategy-per-value model with integrated shrinking; slower generation than quickcheck. SOURCED (search summaries of crate docs/skill pages, e.g. https://awesome.ecosyste.ms/projects/github.com%2FBurntSushi%2Fquickcheck, https://tessl.io/registry/testland/proptest-testing/skills).
- quickcheck: high throughput, per-type generators, weak shrinking for user types unless hand-written. SOURCED (same).
- bolero: one harness runs under libfuzzer/honggfuzz/AFL and Kani. Useful if you want PBT plus fuzzing plus model checking from one test. SOURCED (same search).
- Hegel (`hegeltest` crate, Antithesis, 2026): a thin Rust client over a Hypothesis (Python) backend. Gets Hypothesis-grade "internal shrinking" (readable minimal examples). Developer preview/beta, breaking changes expected, and it REQUIRES A PYTHON INSTALL. The author says the bug examples were written by Claude and ships an agent skill for writing PBTs. SOURCED: https://antithesis.com/blog/2026/hegel/ , https://docs.rs/hegeltest. Fast-moving versions (0.14 to 0.29 on docs.rs) = unstable API; pinning needed.
- Kani (model checking, bounded) and cargo-mutants (mutation testing): exist and are used. Kani proves properties only within bounds and is poor on floating point and big loops (KNOWLEDGE). Floating-point statistical code is Kani's worst case. UNSOURCED for 2026 specifics.
- cargo-mutants: `--in-diff` mutates only code overlapping a diff; `--test-tool=nextest`; `--shard` for CI. Incremental builds + parallelism; one source reports ~15 minutes for a whole project. SOURCED: https://mutants.rs/in-diff.html , https://mutants.rs/pr-diff.html , https://lwn.net/Articles/995276.
- Shrinking quality ranking: Hypothesis/Hegel > proptest > quickcheck (SOURCED above, qualitative only). No head-to-head speed numbers found: UNSOURCED.
- How well LLM agents write them in Rust: no Rust-specific study found. UNSOURCED. All agent PBT evidence is Python/Hypothesis (see 1b).
- Statistical-code caveat (KNOWLEDGE): properties for numeric code need tolerance (relative/ULP), generators that avoid NaN/inf/ill-conditioning, and fixed seeds for reproducibility. Most "invariants" of a fitted model (e.g. score equations ~ 0, invariance to row order, scale equivariance) hold only to a tolerance, and the tolerance itself is a spec decision that an auditor can get wrong.

## Q1b. Workflows requiring a failing test per finding

Published/shipped:
- ReviewGate/Agentboard and EdgeVerdict (PyPI): LLM proposes edge-case tests from intent + diff; a deterministic harness runs them in a clean checkout; a finding counts only if the test compiles, runs and fails. Reports BROKEN / HELD / STOPPED, and "HELD" is explicitly "quantified absence, never certification". SOURCED: https://pypi.org/project/reviewgate/ , https://pypi.org/project/edgeverdict/. Small hobby-scale tools; no published precision numbers: UNSOURCED.
- Agentic PBT (arXiv 2510.09907): agent infers properties from code+docs for 100 Python packages, writes Hypothesis tests, runs them, reflects, files bug report. 56% of reports valid bugs, 32% worth reporting; top-ranked 21: 86% valid, 81% reportable; 5 reported, 3 patches merged (NumPy, cloud SDKs). So even with an executable reproducer, roughly half the "failing tests" were wrong or not real bugs. SOURCED: https://arxiv.org/abs/2510.09907. Cause of false positives not detailed in the paper; likely over-inferred properties (inference, not sourced).
- PBT-Bench (arXiv 2605.15229): 100 problems, 40 Python projects; bug detection 42-83% with Hypothesis scaffolding, 31-77% without; models fail on different problems (boundary bugs, stateful cross-function protocol violations); structured prompts help weak models >20 points, can hurt strong ones. SOURCED: https://arxiv.org/abs/2605.15229.
- Early study "Can LLMs write good property-based tests?" (2307.04346): properties frequently trivial or incorrect (older models). SOURCED: https://arxiv.org/pdf/2307.04346.
- Oracle problem: LLM-generated oracles tend to capture actual not expected behaviour (<50% accuracy classifying oracles, Java); tests written after seeing the code replicate its faults ("code-first oracle bias"); mitigation = write tests from the spec with the code withheld, tests first. SOURCED: https://arxiv.org/html/2410.21136v1 , https://arxiv.org/html/2412.14137v1 , https://agentpatterns.ai/anti-patterns/code-first-test-oracle-bias/. This is directly your TDD design; it also cuts against an auditor who reads the code and then writes a "counterexample".

Failure modes to expect (mix of sourced and my inference):
1. Test asserts the wrong thing / encodes the reviewer's misreading of the spec. Sourced in spirit (56% validity). A failing test only proves disagreement between test and code, not which is wrong.
2. Reproducer fails for the wrong reason (generator produces invalid inputs, NaN, tolerance too tight). KNOWLEDGE.
3. Flaky reproducers: random seeds. Mitigate by persisting the shrunk counterexample as a fixed regression case and requiring it to fail on N reruns. KNOWLEDGE.
4. "HELD" is not evidence of correctness; an auditor that cannot find a counterexample proves little.
5. Defect classes with no property (missing feature, wrong units in docs, performance) produce no test and silently drop out of the audit. This is the biggest design risk: a mandatory-test rule biases findings toward testable ones.

Verdict: "finding = failing test" is sound as a FILTER (cuts prose speculation, gives the adjudicator something to run) and unsound as a TRUTH CRITERION. Keep a human/adjudicator step that decides whether the test is right. Route prose-only findings through a separate, labelled channel rather than dropping them.

## Q1c. Spec format and traceability

Needs: stable requirement ID; property statement in a restricted vocabulary (quantifiers over typed generators, preconditions, tolerance, oracle/reference source); link fields (test path, generator, status); versioning of the requirement (a changed requirement invalidates its test); a "reference oracle" field for stats code (e.g. "matches R `glm` to 1e-8 on fixture X").

Existing tools (Rust-centred, SOURCED via search listing): mantra (manual IDs in code/tests, trace DB), qa (requirements as code, attribute macro links tests, generates matrix), cargo-ovft/OpenFastTrace (`[impl->req-id]` comments), trace-doc (types, Sphinx-Needs export planned). https://lib.rs/crates/mantra , https://docs.rs/crate/qa/latest , https://rust-digger.code-maven.com/crates/cargo-ovft , https://docs.rs/crate/trace-doc/latest. Also Sphinx-Needs and OpenFastTrace generally (KNOWLEDGE). All are small, low-adoption crates; maturity UNSOURCED. Gherkin/BDD (cucumber-rs) links scenarios to steps but states examples, not properties (KNOWLEDGE). Contracts crates (`contracts`, Kani contracts, Prusti/Creusot) give pre/post conditions in code, not in a data spec (KNOWLEDGE).

Practical or a trap? Traceability as a CHECK (every requirement ID appears in at least one test; every test cites an ID) is practical and cheap: a grep-level script. Properties written IN the YAML as executable expressions is a trap: you end up inventing a DSL that is weaker than Rust and needs its own interpreter, tests, and agent training. Do this instead: YAML holds ID + prose statement + tolerance + pointer, and the property lives in a Rust test annotated with the ID; the gate checks the link both ways. Stat-code properties (convergence, tolerance, conditioning) do not fit a declarative DSL.

## Q1d. Why mechanical gates are slow; scoping

- Rust compile is the dominant cost (full build and link per test binary); each mutant needs an incremental build (SOURCED: qaskills/mutants.rs summaries). Per-test-binary link time scales with the number of integration test files (KNOWLEDGE: consolidate tests into fewer binaries).
- nextest: up to ~3x faster than `cargo test` (example 8.4 s vs 2.9 s), bigger on larger workspaces; process-per-test isolation. SOURCED: https://nexte.st/book/benchmarks , https://blog.jetbrains.com/rust/2026/05/01/faster-rust-tests-with-cargo-nextest/.
- sccache: content-addressed compiler cache; up to ~50% better than rust-cache at high hit rates in CI. SOURCED: https://depot.dev/blog/sccache-in-github-actions. Helps cold/ephemeral checkouts; little help to incremental local loops (KNOWLEDGE).
- `cargo check` is much faster than build (no codegen) and is the cheap gate for agent loops; SOURCED qualitatively (cargo docs), no number.
- Affected-test selection: cargo has no native one. Nextest has `--partition`, filtersets (`-E 'rdeps(crate)'`) to run tests of crates depending on changed crates. KNOWLEDGE (nextest filtersets exist; verify). Granularity is crate, not test; within one crate everything reruns. Fine-grained test impact analysis (coverage-based) for Rust: UNSOURCED.
- Mutation: `--in-diff` and `--shard` (SOURCED). Run mutants only on diff, only at checkpoints. Whole-project run ~15 min for one project (SOURCED, not representative).
- Property tests add cost: default 256 cases per test; tune case count per tier (fast in the loop, high in the checkpoint) (KNOWLEDGE).
- Rough numbers for agent loops specifically: UNSOURCED.

## Q2a. Are agents better in Rust than Python?

- Against: Multi-SWE-bench (2025): resolve rates Python ~36-48% vs Rust ~5-8% across models; best agent ~12% on Rust. SOURCED: https://arxiv.org/pdf/2504.02605. These are issue-resolution on existing repos, 2025 models; they confound language with repo difficulty and are dated for a 2026 build. Rust-SWE-bench (2602.22764): 500 tasks, best specialised agent 28.6%, baselines up to 21.2%; failure modes: repo comprehension and type/trait compliance; issue reproduction helped. SOURCED: https://arxiv.org/abs/2602.22764. No cross-language comparison there.
- Training data: Rust is "low-resource" relative to Python in MultiPL-E style studies (older models). SOURCED: https://arxiv.org/html/2410.03981v3. Likely smaller gap for 2026 frontier models, but no 2026 number found: UNSOURCED.
- For: practitioner claims that the compiler is a deterministic, exhaustive free gate and `cargo check` gives a tight feedback loop; "if it compiles it probably works". SOURCED, anecdotal: https://dev.to/tigranbs/coding-rust-with-claude-code-and-codex-2c4j , https://dev.classmethod.jp/en/articles/claude-code-4-languages-comparison/. Same sources: unwrap sprawl, Arc<Mutex>/Rc<RefCell> mixing in async, undocumented unsafe; borrow-checker failures that the agent did not anticipate.
- No controlled 2025-26 study showing agents are better in Rust than Python end-to-end: UNSOURCED. The "free gate" argument is plausible but compile success says nothing about numerical correctness, which is the owner's actual risk. Types catch shape/ownership errors, not wrong statistics.

## Q2b. Stats/data libraries in Rust vs R

- Solid: polars (mainstream DataFrame, lazy, Arrow; SOURCED, Wikipedia/search), ndarray, nalgebra, faer (fast dense linear algebra), argmin (optimisation), statrs (distributions, basic descriptive; KNOWLEDGE for faer/argmin/statrs quality, only listed names surfaced in search).
- Thin: linfa and smartcore are scikit-learn-like ML, not inferential statistics (SOURCED listing). Bayesian/MCMC: small crates (mini-mcmc with NUTS/HMC and diagnostics, bayes-rs, `mcmc` diagnostics crate) (SOURCED: https://docs.rs/mini-mcmc , https://docs.rs/crate/bayes-rs/0.3.0). Nothing comparable to Stan/brms found; maturity of nuts-rs/rv UNSOURCED here.
- Emerging, unproven: `fastglmm` (R package with a Rust backend, lme4-style formulas, LMM/GLMM) and a Cox PH crate with elastic net (cox-hazards) exist but are new, single-author, low-adoption (SOURCED listings: https://pawlenartowicz.r-universe.dev/api/packages/fastglmm , https://docs.rs/cox-hazards). Treat as unvalidated against lme4/survival.
- Missing or unsourced: robust GLM families with full inference output (profile CIs, quasi-families, offsets, weights), mixed models equal to lme4/glmmTMB, survival beyond basic Cox (competing risks, frailty), time series (ARIMA/ETS/state-space vs forecast/fable), GAMs, multiple imputation, survey methods. I found no mature Rust equivalent for any: treat as MISSING (evidence is absence of search hits plus the sourced claim that lme4/survival are "unmatched by Rust alternatives" from a low-quality guide; https://dev.to/piya__c204c9e90/is-rust-good-for-data-science-a-complete-2025-guide-ppn).
- For a statistician the gap is not speed but validated numerics and decades of edge-case fixes in R packages. Reimplementing a GLM or mixed model in Rust means you now own its numerical correctness; the agent's tests would be checking against what? Against R, which brings you back to R.

## Q2c. Calling R/Julia from Rust

- extendr (Rust inside R packages; mainly R calling Rust, not Rust calling R). CRAN has a Rust policy discussion (vendoring, toolchain); SOURCED: https://stat.ethz.ch/pipermail/r-devel/2025-March/083861.html . Embedding R in a Rust binary (libR-sys): R is single-threaded, global-state, not reentrant, needs R_HOME and matching libR at build/run; fragile (KNOWLEDGE). Poor for an automated gate: crashes take down the process.
- jlrs (Rust embeds Julia): Julia calls must be single-threaded from one thread; supports Julia 1.10-1.12 only (LTS + stable tested). SOURCED: https://docs.rs/jlrs/ . Large Julia startup/precompile time and runtime in the process (KNOWLEDGE). Fragile deployment.
- PyO3: robust and well-used, pulls in Python runtime (KNOWLEDGE); only relevant if keeping Python.
- Subprocess (Rscript/julia script, exchange via Parquet/Arrow IPC/JSON/CSV): the sound option for an automated gate. Process isolation, crash = nonzero exit, easy to run in tests, version-pinnable (renv/lockfile, Julia Project.toml), data frames round-trip via Arrow/Parquet. No public source for this as a recommended pattern: UNSOURCED, my judgement.
- Sharp edges of the subprocess pattern (KNOWLEDGE): R/Julia startup cost (R ~0.2-0.5 s, Julia seconds unless sysimage/PackageCompiler) per call, so batch work, don't call per row; floating-point round-trip (use Parquet/Arrow binary, not CSV/JSON, or write hex/17-digit floats); factor/NA/NaN/Inf/date-time semantics differ across the boundary; locale and RNG streams (seed handling must be explicit, R's and Rust's generators differ); stdout pollution (warnings, package startup messages) corrupting JSON; R packages need a pinned library and CRAN/binary availability on the build machine; CI image must carry R/Julia; warnings are not errors by default so set `options(warn=2)` or capture them; exit codes and partial output; timeouts and zombie processes. Gate impact: each R call is slow and non-hermetic, so agent loops should mock the boundary and run real R only in the checkpoint tier.
- Upside: the R script becomes a reference oracle for property tests ("Rust result agrees with R's glm within tol on generated data"). Cached golden fixtures (generated once by R, committed) keep the fast gate hermetic.

## Q2d. Recommendation and strongest counter-argument

Recommendation:
1. Do NOT make Rust the only target on the strength of "compiler as free gate". Make the workflow language-neutral at the spec layer, and treat Rust as one supported target, chosen per package when the code is performance- or correctness-critical and the numerics are simple or have R/Julia reference fixtures. Keep R packages as R (testthat, covr/mutation via `mutatr`-style tools: UNSOURCED) because that is where the stats libraries and validated numerics are. The owner's stack is statistical; the library gap (Q2b) is the dominant fact.
2. Adopt the audit rule in a weakened form: every behavioural finding must carry a runnable reproducer OR be filed as an explicit "no-test" finding with a reason; adjudicator decides test-validity before the finding counts; counterexamples are saved as fixed regression cases and rerun to confirm determinism. Write tests from the spec with the code withheld (sourced oracle-bias mitigation).
3. Specs: YAML for IDs, prose, tolerances, reference-oracle pointers; properties as code; mechanical two-way ID check. Do not build a property DSL.
4. Property-test tooling in Rust: proptest as default; consider bolero only if you want fuzz+Kani from one harness; evaluate Hegel only as a preview (Python dependency, unstable API). cargo-mutants `--in-diff` at checkpoints only; nextest + `cargo check` in the inner loop; sccache for cold CI.
5. Gate tiers: check (seconds) > affected crate nextest with low proptest cases > full + high cases + mutation in-diff at checkpoints > R-oracle/canary tier.

Strongest argument against this recommendation: a language-neutral workflow means the harness must stay thin and generic and cannot exploit Rust's strengths; you pay a permanent cost in tool abstraction (two test runners, two mutation tools, two property libraries) and Python/R lack a free type/borrow gate, so agents there fail later and more silently. If most new code is greenfield numerical kernels where agents get a hard compile-time gate, a Rust-only workflow with R as an out-of-process oracle gives a simpler, faster, more reliable harness, and the missing-library problem is rare for the small set of methods the owner actually ships. If the owner's real deliverables are things like mixed models and survival analyses, the counter-argument loses; if they are data pipelines and simulation kernels, it wins. I could not source the share of the owner's work in each bucket; that decides it.
