# Claude Code mods: what they make possible for a self-compacting orchestrator

Researched 2026-10-06. Sources: https://code.claude.com/docs/en/plugins/mods/{overview,create,events,api,reference,interface,troubleshoot,admin}, https://code.claude.com/docs/en/{hooks,checkpointing,commands,prompt-caching,headless,agent-sdk/slash-commands}, and the engine-written declarations bundled with the `plugin-authoring` skill (build 2.1.289), file `types/claude-code.d.ts` (20,426 lines), plus its `reference.md`. Items marked INFERRED are my reading, not stated in docs. "Types" = that d.ts file (docs say it is the authority; the reference page itself says "trust these files over any page").

## Headline

- Answer to the central question: a mod can programmatically COMPACT with no keypress (`$.session.compact({ instructions })`), and can read context usage (`$.session.usage()`), so threshold-triggered compaction is a documented, supported feature.
- A mod can NOT rewind. There is no rewind, clear or fork API in the mods API, and the plain settings hooks page states hooks cannot trigger them. The nearest things are: (a) `session.compact` with a rewritten `messages` list (replace the transcript with whatever you want, including checkpoint file contents), (b) `$.command.run({command: 'clear' | 'branch' | 'fork' ...})`, which is documented to run "a slash command as if the person typed" but whose behaviour for the built-ins clear/rewind is NOT documented (INFERRED possible, untested), (c) git for files.

## 1. What a mod is, packaging, language, hooks, powers

Definition. Overview: "A mod is a plugin that changes how Claude Code looks and behaves. It's made of JavaScript or TypeScript event handlers: Claude Code calls one when an event happens ... and the handler can watch the event, change it, or take it over." (/plugins/mods/overview). A hook is "a function that runs inside Claude Code instead" of a shell command (settings hooks run as shell/HTTP/prompt; mods are in-process).

Packaging (reference#files): `.claude-plugin/plugin.json` (normal manifest), `hooks/hooks.json` with `"modules": ["./register.js"]` ("an array with one path"), the hooks module (`.js .mjs .cjs .jsx .ts .mts .cts .tsx`, ES module, exports `register(on, options)`), optional `types/index.d.ts` (needed for `$.state`), optional `*.test.ts`. No Node, no bundler: "Claude Code loads .js and .ts files directly". Loaded by `claude --plugin-dir <dir>` (hot reloads on save), by install from a marketplace (`/plugin install x@mkt`, then `/reload-plugins`), or `CLAUDE_CODE_PLUGIN_DIRS`. Sandbox: "The hooks module itself has no Node.js APIs, no timer globals such as setTimeout, and no network or file access of its own"; everything goes through `$` (api page). "Mods aren't sandboxed" and run with user permissions (overview#decide-whether-to-trust-a-mod).

Hook shape: `on(event, matcher?, ($, e, next) => result)`; `next(e)` continues down a middleware chain; return without `next` to answer yourself; `next({...e, x})` to rewrite. "A hook can observe, rewrite, or answer" (overview#what-a-hook-can-do-with-an-event).

Full event list (reference#events; types agree):
- Tools: `tool.call` (return `next(e)`, `{deny}`, `{result}`; can rewrite arguments; applies to subagents' calls and MCP calls too), `tool.check` (`{decision: allow|ask|deny}`), `tool.describe`.
- Prompts/what Claude reads: `prompt.submit` (rewrite `text`, add hidden `context`, or `{drop}`), `prompt.fill`, `prompt.suggest`, `prompt.edit`, `prompt.compose` (system prompt sections), `prompt.section`, `prompt.context` (context blocks sent with first message), `prompt.attachment` (engine reminders), `skill.prompt`, `attribution.text`.
- Commands/config: `command.run`, `command.describe`, `config.set`, `config.describe`.
- Turns: `turn.start`, `turn.step` (streaming; "Read each request's token usage, send it to a different model with next({...e, model}), or answer without calling the model"), `turn.complete` (has `e.answer`, `e.usage`, `e.isAborted`, `e.agentId`).
- Session: `session.start` ("Not after /clear, /resume, or /branch"), `session.end` (`e.reason` clear|resume|logout|prompt_input_exit|other), `session.compact`, `session.receive`/`session.send` (cross-session messages), `session.append` (every row stored; rewrite content), `session.attach`/`detach`, `session.measure` ("After each turn, and when a plan limit's percent used changes").
- Subagents: `agent.offer`, `agent.spawn`.
- UI: `ui.render`, `ui.resolve`, `ui.press/input/select/focus/scroll/close/message/fault`.
- Other mods: `plugin.register`, `engine.create`. Telemetry: `telemetry.log/mark`.
- Settings-hook events as `classic.<Event>` ("e is the hook's stdin JSON"; includes `classic.Stop`, `classic.PreCompact`, `classic.PostCompact`, `classic.SessionStart` etc.).
- Every `$` API call is itself an event (`fs.read`, `model.complete`...), hookable by earlier mods.

`$` namespaces (reference#mods-api-methods): `$.ui` (resolve, invalidate, open, close, panes, focus, scroll, toast, status, log, notice, ask, copy, selection, blit), `$.command` (register, run, list), `$.tool` (register, call, check, list), `$.agent` (register, spawn, list), `$.model` (complete, fork, classify), `$.prompt` (submit, read, fill, suggest, compose), `$.turn.abort`, `$.session` (messages, cwd, root, model, turns, id, repo, surfaces, usage, version, compact, send, append, authorize), `$.config`, `$.settings.read`, `$.env`, `$.fs`, `$.store`, `$.state`, `$.clock` (now, sleep, after, every), `$.http.fetch`, `$.process` (run, spawn), `$.mcp` (call, connect), `$.audio`, `$.telemetry`.

Read/change by hook: each event's `e` is deeply frozen plain data and you pass a modified copy to `next`; some fields are "pinned" (changing them fails the hook). Specifics are in section 4 and 5.

## 2. Programmatic rewind / clear / compact / fork (the key question)

COMPACT: YES. Types (`$.session.compact`): "Compacts the conversation: the event `session.compact` with `trigger` `plugin`, the same call `/compact` makes, between turns. It runs through every hook but the calling one, then core: a summary and the kept messages in the transcript's place. Resolves `{ skip }` when a hook vetoed it; rejects while a turn runs." Signature: `$.session.compact({ instructions?: string })`, returns `{ messages, tokensBefore?, tokensAfter?, usage? } | { skip }`. Example in the docs' own types: `const { skip } = await $.session.compact({ instructions: "the plan" })`. Only argument is `instructions` ("What the summary should keep or stress, as typed after /compact"). The `session.compact` event also fires for `/compact` (manual), the engine threshold (auto), and a `precompute` (a speculative compaction whose result is "kept for the next compaction").

Caveat that matters for an orchestrator: it "rejects while a turn runs", so the call must be made when idle: e.g. from a `$.clock.after` timer after `turn.complete`, or from a `command.run` handler. INFERRED pattern: `on('turn.complete')` then `$.clock.after(0, ...)` to compact when idle.

CLEAR: no dedicated API. Observation only: `session.end` with `reason: 'clear'` and `classic.SessionStart` with `source: 'clear'` fire after a person runs `/clear` (interface#load-a-saved-value-again-after-clear; "Those commands reset every $.state value to its default, and session.start doesn't fire again"). Attempt path: `$.command.run({ command: 'clear' })`. Types: "Runs a slash command as if the person typed `/command args`: the event `command.run`, queued and run once the session is idle ... Rejects an unknown name, and inside a hook the turn is waiting on." and `$.command.list()` is "built-in, plugin and MCP alike". So running the built-in `/clear` this way is plausible but NOT documented: INFERRED, needs a spike. In `-p`/SDK, docs say sending `/clear` as a prompt works in streaming-input mode (agent-sdk/slash-commands: "The /clear command resets the conversation to an empty context"), which is a driver-side route, not a mod.

REWIND: NO. The mods API has no rewind/restore/truncate method (grep of the 20k-line types for rewind/restore/truncat finds nothing relevant). The hooks page says outright: "Hooks cannot trigger /clear, /compact, or /rewind operations ... These operations must be initiated by Claude or the user." (/hooks, as summarised by fetch; that statement is about settings hooks and predates mods; it is contradicted for /compact by `$.session.compact`, so treat it as stale for mods but accurate for rewind and clear). `/rewind` is a human menu (checkpointing page: "Run /rewind, or press Esc twice ... The rewind menu lists the prompts you sent"). Named earlier points: only via that picker (by prompt); not documented as addressable by name or id from code. A rewind equivalent by `$.command.run({command:'rewind'})` is unlikely to work since it opens a picker (INFERRED).

Nearest equivalent to "rewind to named point + re-inject": `session.compact` hook that answers with its own `messages`. Types: "Rewrite `instructions` or `messages` on the way down, the messages on the way up, or answer `{ messages }` of your own". `SessionCompactInput.messages` is the transcript (each with the engine `handle`); `next({...e, messages})` "changes what is summarized: a message kept with its handle is the engine's own, whole; one without is read as built". Result type note: "There is no summary string: the summary is a message." So a mod can replace the post-compaction transcript with an arbitrary list built from `{role, text}` (a hand-written summary plus checkpoint file contents plus the last N engine messages by handle). That is the closest thing to "reset to a clean state and re-inject checkpoints". Whether messages built without handles fully work, and whether it is cheaper than a real clear, is INFERRED and needs a spike.

FORK of conversation: no programmatic fork that creates a new conversation. Available: `$.model.fork({ prompt })`, a one-shot tool-less question over the current transcript (same model and system prompt, served from prompt cache, result `nothing-to-fork` right after /clear); `$.agent.spawn` and the Agent tool's `fork` subagent type ("True for a fork of the parent: it inherits the parent's context and model", AgentSpawnInput.fork); user `/branch`, `/fork` commands (commands page) whose programmatic triggering is, again, only possible via the undocumented `$.command.run` (INFERRED).

Files vs conversation: checkpointing page: rewind has separate options "Restore code and conversation", "Restore conversation", "Restore code", "Summarize from here", "Summarize up to here" (so they ARE separable, but only in the human menu). Limits: "Checkpointing does not track files modified by Bash commands"; subagent edits not restored; "Not a replacement for version control". For a build tool, git is the only reliable file-state mechanism.

## 3. Reading context usage and acting on a threshold: YES

`$.session.usage()` returns `{ startedAt, context, rateLimits, cost }`; reference: "`context` has `tokens`, `window`, and `percent`". Types doc example (verbatim): `const { context } = await $.session.usage(); if ((context.percent ?? 0) >= 85) await $.session.compact()`. `usage({breakdown: 'full'|'summary'})` adds the /context category breakdown (system prompt, messages, free space, `autoCompactThreshold`, `isAutoCompactEnabled`, autocompact window). Caveat from the types: `tokens` and `percent` are "the last API response's input side", "absent until the first response of the live window: a fresh session, or one just compacted, until its next response." Other signals: `turn.step` result `usage` (per-request input/output/cache tokens), `turn.complete` `e.usage`, `session.measure` (after each turn). Docs' own sample mod `token-weather` "draws a forecast of your context window".

Autocompaction itself is separate engine behaviour; a `session.compact` hook with `{ trigger: 'auto' }` matcher can shape or veto it (`{ skip }`). The compaction window can be set by `CLAUDE_CODE_AUTO_COMPACT_WINDOW` / settings (types, ContextWindowSource) (settings-level, not mod API).

## 4. Injecting content / shaping compaction / what survives

Documented ways to put content in context:
- `$.session.append({ message: { type: 'user', content: [text blocks] } })`: "REALLY appends: a user-role row the person does not see as typed (stored isMeta, the model reads it)" (reference.md). Text blocks only; to main conversation or a running subagent. This is the clean post-compact/post-clear re-injection call. (Whether it is allowed immediately after compaction/clear is INFERRED; the docs only say "The row is in the list at once and in a running turn's requests from the loop's next top.")
- `prompt.submit` hook: `next({...e, context: [...]})` adds text only Claude reads after the prompt. `$.prompt.submit({text, asUser?})` starts a new turn when idle: "queues a prompt that starts a turn of its own once the session is idle (never folded into a running turn ...)". With `asUser: true` it is sent "as the user's own words".
- `prompt.context` (blocks sent with the first message, per conversation), `prompt.compose`/`prompt.section` (system prompt sections; "Text from these hooks that changes between requests invalidates the prompt cache"), `prompt.attachment`.
- `command.run` result `{ text, context: [..] }`: `context` is "what the model reads after the command's output and the person never sees".
- Settings-hook route: `classic.SessionStart` with `source` `compact` or `clear` and `additionalContext` ("Start of conversation, before first prompt", max 10,000 chars per field) (hooks page).
- `session.append` hook can also rewrite any row (including `door: 'compaction'` rows, i.e. the compaction boundary and summary) with `next({...e, message})`; thinking and tool_use blocks are put back.

Compaction shaping: `session.compact` hook (input: `trigger`, `agentId?`, `instructions?`, `messages`). Can change `instructions` (what the summarizer is told), change `messages` (what is summarized), answer with `{ messages }` of its own (becomes the transcript), or `{ skip: reason }`. Result carries `tokensBefore/After` and the summarizer's `usage`. Contrast: classic `PreCompact` "Cannot modify custom instructions", can only block; `PostCompact` has no decision control; `additionalContext` has no effect on either (hooks page). So mods are strictly more capable than settings hooks here.

What survives compaction by default: see https://code.claude.com/docs/en/context-window#what-survives-compaction (linked from commands page; I did not fetch it). NOT READ in detail.

Mod-state storage: `$.store` (JSON, cross-session, shared by all sessions on the machine, 4 MiB) and `$.state` (session-long, reset by /clear, /resume, /branch). The mod can also just `$.fs.read`/`write` the checkpoint files (4 MiB per file).

## 5. Sub-agent dispatch

- Intercept/shape: `agent.spawn` hook: input `{ prompt, description, subagentType, model?, background, cwd?, name?, parentModel, fork, isTeammate, ... }`. "A hook rewrites content (prompt, description, subagentType, model, background, cwd), read back as the tool's parameters." Return `next({...e, model})` to choose model, or `{ deny: reason }`. Pinned: tool_use_id, name, fork, isTeammate, parentModel, permissionMode, parentAgentId, provider. Rewriting `subagentType` to another dispatchable agent changes its tool set indirectly. A direct "tools" override on a single spawn is NOT documented; tools come from the agent definition.
- Define agent types: `$.agent.register` ("from an agent definition as settings JSON spells one (prompt, tools, model, and the rest, all in force)"), `agents/*.md` in the plugin, and `agent.offer` to withhold types from the model.
- Run sub-agents yourself: `$.agent.spawn({ prompt, subagentType?, model?, cwd?, name?, description? })`, "runs one and its answer is its `turn.complete`" (reference.md). `$.agent.list()` lists them.
- See results before the main model: yes. `tool.call` on the Agent tool: `await next(e)` returns the result and a hook may rewrite it before the model reads it (events page: "Claude's view of the call doesn't change, because the hook returns the result it received", i.e. it can change it). `turn.complete` fires for subagents with `e.agentId`; `$.session.messages({ agentId })` reads a subagent's transcript; `turn.step` runs for subagent requests (`e.agentId`) so a mod can switch their model or answer without calling one. Also `tool.call` fires for the subagents' own tool calls.
- Cross-agent messaging: `$.session.send({ to: { agentId } | { sessionId }, text })`; `session.receive` hook can `{ consumed }` a message.
- Subagent compaction: `session.compact` input has `agentId` ("for a subagent's or a fork's own transcript").

## 6. Headless / Agent SDK / remote

Overview table (/plugins/mods/overview#where-mods-run): hooks run in terminal (yes, draws), Desktop Code tab (yes, draws), VS Code panel ("Yes", no drawing), "`claude -p` and the Agent SDK | Yes | No", Remote Control ("Yes, in the session on your machine"), cloud sessions ("Yes, for a plugin that reaches the cloud session"), WSL desktop sessions: no. So the logic hooks (compact, usage, session.append, prompt.submit, agent.spawn, session.compact) run headless; only drawing doesn't.

Headless caveats: `--bare` skips auto-discovery of hooks and installed plugins, but "A plugin | --plugin-dir <path>, --plugin-url <url>" still loads (headless page). `$.ui.ask` rejects in `claude -p` (events page). A mod Claude itself writes (hot-reload dev-mods folder) "doesn't load" under `-p` (create#sessions-that-skip-the-approval); so for autonomous runs ship the mod as an installed plugin or `--plugin-dir`. Long-lived SDK/desktop sessions only reload on save with `CLAUDE_CODE_PLUGIN_DIR_WATCH=1`. A `command.run` result can set `exitCode` for `claude -p "/lint"` runs. `claude -p` + `--plugin-dir`: failures printed to stderr. Plugin load status shows in `system/init` (`plugins`, `plugin_errors`). In SDK, `/compact` and `/clear` can also be sent by the driver as prompts (agent-sdk/slash-commands): `/compact` via `query({prompt:'/compact', options:{continue:true}})` yields a `compact_boundary` system message; `/clear` works "in streaming input mode". That is the non-mod, external-driver alternative.

Not checked: whether `$.session.compact` specifically works inside `-p`; docs list hooks as running but don't test this call. INFERRED yes.

## 7. Prompt cache

From /prompt-caching:
- Compact: "Compaction replaces your message history with a summary. By design, this invalidates the conversation layer, since the next request has a new, shorter history that doesn't share a prefix with the old one." System prompt layer reused; project context reloaded from disk ("which cache-hits only if CLAUDE.md and memory are unchanged"). The compaction request itself reuses the warm cache ("While the cache is warm, that request reads your prefix from the cache"); after a gap longer than the TTL "the summarization request reprocesses the full history as uncached input".
- Rewind: "/rewind truncates your conversation back to an earlier turn. The remaining history is the same content the cache was built from at that point ... so the next request hits the earlier cache entry." and "Restoring file checkpoints alongside the conversation has no separate effect on the cache." Tip: "If you've gone down a path you want to abandon entirely, /rewind to an earlier turn instead. Rewinding truncates back to a prefix that is already cached, rather than building a new one as compaction does." (So rewind is the cache-friendly operation, and it is the one a mod cannot do.)
- Clear: project-context layer "Changes when ... Session starts, or after /clear or /compact". A clear starts a fresh prefix (INFERRED: system prompt layer is shared, rest rebuilt).
- Mod-specific: rewriting system prompt sections or context text that changes between requests invalidates the cache (events page). Adding plugin skills/commands/agents/hooks/monitors "never invalidates the cache" but a plugin that adds MCP servers behaves like an MCP server change; mods' registered tools via `$.tool.register` appear as `mcp__<plugin>__<name>` tools (INFERRED: tool-definition changes mid-session can invalidate the system-prompt layer when tool search is not deferring them).
- Cache TTL: 5 min default; 1 hour only for subscription main conversation within plan usage; setting `promptCacheTtl`. Compaction/forks/subagents are "Everything else" bucket (5 min unless `subagentPromptCacheTtl`).
- `$.model.fork` is cache-friendly: "same model and system prompt, so the API serves that prefix from its prompt cache (`usage.cache_read_input_tokens` says how much it served)".
- Cost note for an autonomous loop: a mod-triggered compaction behaves like `/compact`: one summarizer request plus a cold conversation layer. Compacting right after a long idle gap costs more.

## 8. Limits, caveats, stability

- Versions: terminal v2.1.287+, Desktop v2.1.286+ (overview#turn-mods-on-or-off); reference page covers "as of v2.1.289". `CLAUDE_CODE_ENABLE_FUNCTION_HOOKS` is ignored in v2.1.287+. Release channel wording: reference.md says "The API is early access and moves between releases: the declaration file is the authority"; docs: "The events and methods can change between releases, so trust these files over any page". The docs pages do not use the word "experimental", but the early-access note plus the fact that docs and types disagree on details (hooks page still says hooks cannot trigger /compact) indicates churn. Anthropic can remotely switch installed mods off ("Anthropic has turned installed mods off remotely", troubleshoot); admins can disable (`allowManagedModsOnly`, `disableAllHooks`, `allowManagedHooksOnly`, `disableSideloadFlags`). `--safe-mode` and `--bare` turn installed mods off.
- Time limits (reference#limits): a hook's own execution 10 s (50 ms for `prompt.edit`), time inside `next` or `$` calls not counted except `$.clock.sleep`; `.catch` handler 1 s; all `session.end` hooks together ~1.5 s; `$.process.run` 30 s default, 10 min max; `$.model.complete` maxTokens 1024 default; `$.fs` 4 MiB; `$.store` 4 MiB; `$.session.messages()` newest 4,096 entries. A hook that throws or times out is skipped (fails open) unless it has a `.catch` handler.
- Worker: installed mods share one worker thread; a blocking hook can crash/unload it; three crashes unload all non-built-in mods for the session ("it crashed 3 times").
- Static analysis constraints: `claude plugin validate` requires literal event names, `$.ns.method(...)` written in full, no `import()`; dynamic code gets refused.
- Compact-specific: `$.session.compact` rejects while a turn runs; `$.command.run` rejects "inside a hook the turn is waiting on".
- Safety rails relevant to an orchestrator: a mod that rewrites a tool call input is flagged in auto mode ("a hook changed this call's input after the model wrote it").
- Test harness: `claude plugin test` (bun-like `claude-code/testing`) runs without a session, so deterministic tests of the compaction policy are possible.

## 9. Other useful features for deterministic control around a model orchestrator

- Autonomous loop driving from inside the session: `$.prompt.submit({text, asUser?})` (starts a turn when idle) plus `$.clock.every/after` timers started in `session.start`: a mod can wake a quiet session and feed the next instruction. `turn.complete` carries `e.answer` and `e.usage` to detect phase ends. Timers "run until cancelled or until the module reloads" and "doesn't start a turn" on their own.
- Blocking a stop: settings-hook route `classic.Stop` (hookable as a mod event): "decision: block with reason ... Prevents stopping, continues conversation" and `additionalContext` (hooks page). Mods' own `turn.complete` cannot block; use `classic.Stop` or just re-submit via `$.prompt.submit`. `$.turn.abort` exists to abort a turn.
- Gating tool calls: `tool.call` `{deny}`/rewrite/`{result}`, `tool.check`. Enforcing workflow rules (e.g. "implementer may not edit tests") is directly doable and deterministic. Hooks in managed settings run first.
- State persistence: `$.store` (cross-session, machine-shared, JSON, 4 MiB, "not atomic" across sessions); `$.state` (session scope, reactive, reset on /clear//resume//branch; reload `$.store` into it from `classic.SessionStart {source: clear|resume|fork}`); `$.fs` for checkpoint files. Module-level variables are lost on every reload.
- Panes/status: `$.ui.open` pane (sidebar in wide fullscreen terminal, otherwise above the prompt), `AbovePrompt` band, `$.ui.status` line, `$.ui.toast`, `$.ui.log`; none render in `-p`/SDK.
- Own commands and tools: `$.command.register` + `command.run` handler returning `{text, context, exitCode}` (e.g. a `/checkpoint` command); `$.tool.register` gives the model a custom tool (listed `mcp__<plugin>__<name>`), e.g. a `checkpoint` or `phase_done` tool the model calls and the mod serves, which can then compact.
- Model calls by the mod: `$.model.complete({model, prompt, ...})` (no history, uses user's plan or key) for summarisation/classification (e.g. Haiku to write the checkpoint summary), `$.model.classify`, `$.model.fork` (cache-friendly question over the live transcript), `turn.step` model rewrite (route requests to a different model).
- Cross-session messaging: `$.session.send` / `session.receive` (message another session by id or a subagent by agent id).
- Run processes and HTTP: `$.process.run/spawn`, `$.http.fetch`, `$.mcp.call`; e.g. run the test gate from a hook.
- Telemetry/cost: `session.measure` (per turn cost and rate limit percent), `$.session.usage().cost`/`rateLimits`.
- Sample mods to copy: https://github.com/anthropics/claude-code-playground/tree/main/claude-code/mods (`token-weather`, `blast-radius`, `replay-theater`); built-in mod sources https://github.com/anthropics/claude-code/tree/main/mods (`diff`, `agents-md`, `sec-default`, `telemetry`); full declarations https://github.com/anthropics/claude-code/blob/main/mods/types/claude-code.d.ts.

## What this means for the successor design (INFERRED, not from docs)

A fully in-process autonomous compaction loop looks feasible today as a mod: `turn.complete` or a timer reads `$.session.usage()`; when idle and past threshold (or at a phase boundary), write checkpoint files with `$.fs.write`, then either `$.session.compact({instructions})` with a `session.compact` hook that injects the checkpoint files into the resulting `messages`, or call `$.session.append` with the checkpoint text after the compaction, then `$.prompt.submit` to continue. What is NOT available: a true rewind-to-named-point (cache-friendly, truncating) or a hard `/clear`. If a clean clear is required, the options are the undocumented `$.command.run({command:'clear'})` (needs a spike) or an external driver (Agent SDK streaming-input mode sending `/clear`, `/compact`, or `resume`/new session with the checkpoint files re-injected as the first prompt), which is the officially documented headless route.

Spikes worth running before committing: (1) `$.command.run({command:'clear'})` and `{command:'compact'}` from a mod under `claude -p`/streaming and interactive; (2) `session.compact` hook answering own `messages` built from `{role,text}` only (no handles): does the next request use exactly that transcript; (3) `$.session.append` immediately after a compaction or clear; (4) `$.session.compact` under `claude -p`; (5) cache cost of (2) versus engine summary.
